# Implementation notes (code-v1.4)

Where the code interprets preregistration-volatility-v1.0.md. Each item is a reading of the document, not a change to it.

1. **History rule.** "First daily Coinbase candle on or before 2023-11-03" is implemented as "at least one daily candle between 2023-01-08 and 2023-11-03" (exactly 300 days, one Coinbase request). It differs only for a coin that traded before 2023 and then had no trades for ten months.
2. **Exclusions.** Explicit symbol lists in `exclusions.json` plus Coinbase's `fx_stablecoin` flag. Liquid-staking tokens (stETH, mSOL and similar) are treated as wrapped tokens, which is an interpretation. WAXL and WCFG are their projects' own tokens under a wrapped-style ticker; they are listed as wrapped by ticker and are unlikely to reach the top 30. The earlier leveraged-token name pattern was removed in v1.1 because it wrongly matched real coins such as JUP; Coinbase lists no leveraged tokens. Every exclusion and its reason is written to `fetch-log.txt`.
3. **Training rows.** A row is used only if its whole target window ended on or before the refit date, its input windows are valid, and all its target days are present and non-void. Void target days are dropped from training and scoring.
4. **7-day scoring.** A forecast is scored only if all 7 target days are present and non-void and the window ends on or before 2026-11-03.
5. **Input windows.** A void day is replaced by the median of the previous 30 non-void days and counts as present. A window mean needs at least ceil(0.8 x length) present days.
6. **Forecast.** HAR forecast = exp(fitted + 0.5 x SSE/(n-k)). The 7-day HAR is a separate regression on the log of the 7-day sum. The 7-day baseline and EWMA are 7 times the one-day values.
7. **Refits.** Every 30 days from an anchor: 2025-11-03 for the locked year, the first day with at least 365 training rows for the development run.
8. **Spike rule.** In Garman-Klass mode a day is flagged if ln(H/L) exceeds 5 times the trailing 30-day median of ln(H/L) (zero-range days excluded from the median). In hourly mode it is flagged if the day's realised variance exceeds 25 times the trailing 30-day median (non-void days). A flagged day is voided only if Kraken has a candle for that day and Kraken's ln(H/L) is below 2 times Kraken's own trailing 30-day median (zero-range days excluded); otherwise it is kept. Kraken pairs are mapped through Kraken's `AssetPairs`, and each coin's Kraken candle count (or the reason there is none) is written to `fetch-log.txt`.
9. **Zero-range days.** A day with high equal to low (or hourly variance at the floor) is void in both target modes.
10. **Scoring.** Per day, the average QLIKE across the coins available that day; the 3% test and the one-sided Diebold-Mariano test (Newey-West lag 6, normal approximation) use that same series. A coin improves if its mean QLIKE is below the baseline's.
11. **One locked call.** A single `--period locked` call computes the main result, EWMA, the run without the spike rule and the Parkinson run, and writes them to one file, so the one-time opening cannot be spent on the wrong configuration. Only the main result decides the verdict.
12. **Code version.** The full fetch runs only if the checked-out commit equals tag `code-v1.2`, and `fetch-log.txt` records the commit hash.
13. **Preview.** `MODE=preview` runs the real coin selection over all Coinbase USD pairs and the Kraken mapping and prints the result as a job summary. It writes nothing and downloads no hourly data. The coin list depends only on volume before the lock, not on any volatility result.
14. **Void log.** The analysis reports spike voids and zero-range or missing-hour voids separately, for the scored period only, and spike voids are not counted in the run without the spike rule.
15. **Ticker-change effect (documented after the preview, before any analysis).** "First daily Coinbase candle" is read literally for the current product. RENDER (was RNDR), POL (was MATIC) and S (was FTM) are excluded because Coinbase's current product starts after 2023-11-03, although the coins have longer history under their old tickers. Joining series across token swaps would be a judgment call the rule exists to avoid, so the rule was kept. The effect is similar to survivorship and is expected to be negligible for a volatility test.
16. **Fetch outcome.** The full fetch (Action run 41809908288, tag `code-v1.2`) selected the same 30 coins as the preview. Hourly coverage was 0.998, so the target is hourly realised variance for all coins. Kraken daily candles: 720 for 27 coins, 644 for CRO and 482 for HBAR; spikes outside Kraken's data are kept.
17. **What counts as a bug (written before the development run).** A bug is code that does not do what the pre-registration says. A surprising number is not a bug, and a bad or good result is never a reason to change anything. The development run is read with these checks, which are for finding bugs only and never for judging or tuning the result:
    - HAR improvement over the baseline of roughly 5-30% is plausible. Above about 50% points to leakage; a negative number points to a broken pipeline.
    - The ratio of mean forecast to mean realised variance should be close to 1. A ratio outside 0.7-1.4 points to a log-correction or units bug.
    - Void counts: spike voids should be a handful (well under 1% of coin-days) and zero-range or missing-hour voids close to zero, given 99.8% hourly coverage.
    - No single coin should dominate the average loss, and the EWMA and Parkinson runs should point the same way as HAR.
    - A bug found is fixed and logged with its reason before the locked year is opened, and the fix gets a new code tag.
18. **Diagnostics (code-v1.3).** The analysis prints per-coin improvement, the forecast-to-realised ratio, last-refit HAR coefficients and void counts per coin. Scoring is unchanged; a test checks that the stored forecast and realised value reproduce the scored loss.
19. **Bug found in the first development run, fixed in code-v1.4.** The spike rule voided 6 days (3 XRP, 3 XLM, 2024-11-15 to 2024-11-22), all in the first week of Kraken's data. There Kraken's trailing 30-day median was built from one or two days, and those days were the spikes themselves, so Kraken's range always looked "normal" against it and real moves were voided although Kraken confirmed them (for example XRP 39.2% on Coinbase and 37.3% on Kraken the same day). The pre-registration voids only single-exchange wicks, so this was a bug. Fix: Kraken's trailing median needs at least 24 of the previous 30 days (the same 80% rule used elsewhere); otherwise the day is kept. This affects only the early development period: in the locked year every coin has months of Kraken history. Kraken alignment was checked at the same time: the Coinbase and Kraken daily ranges correlate most strongly at lag 0 for every coin (0.69-0.99), so the candles are aligned. The first development run (code-v1.3, commit a219e74) is kept in the history.
20. **Forward logger (see `forward/README.md` and `preregistration-forward-v1.0.md`).** The runner re-implements the next-day HAR forecast because `lib.mjs` must stay byte-identical to `code-v1.4`; a test checks that it reproduces `lib.forecastCoin` exactly at 1 and 7 days across refits. A run before D0 only fetches data and extends the digest chain. If the data for day t is short, the run retries until 02:00 UTC and then predicts from what is available, recording the hour count. The ledger is one file per month; each digest line names the lines it covers, so the check also catches deleted or extra lines. Scoring marks a window with a missing or void day as void and never drops it silently.
